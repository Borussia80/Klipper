## Crítico (histórico, já remediado)

### C1 — `secret_key_base`/`master.key` expostos no histórico do repositório público

- **Onde:** `config/master.key` foi commitado desde `46e7e1b`, presente em
  todo o histórico até a reescrita.
- **Impacto:** qualquer pessoa com acesso ao repositório (público no GitHub)
  podia extrair a chave e forjar um JWT válido para qualquer `user_id`
  (`JwtService::SECRET = Rails.application.secret_key_base`, algoritmo
  HS256 simétrico) — comprometimento total de autenticação.
- **Status:** **remediado** em `c2742d3` (2026-07-09) via `git-filter-repo`
  (reescrita de todo o histórico) + rotação da chave em produção.
- **Risco residual:** clones/forks feitos antes da reescrita podem reter
  objetos "soltos" (dangling) por até a janela de retenção padrão do GitHub
  (~90 dias); irrelevante desde que a chave tenha sido rotacionada — um
  `master.key` antigo não decodifica/assina nada em produção depois da
  rotação.
- **CWE:** CWE-798 (Use of Hard-coded Credentials).

## Alto

### H1 — BOLA: `Budget` aceita `category_id` de outro usuário, exposto via `#summary`

- **Onde:** `app/controllers/api/v1/budgets_controller.rb` — `budget_params`
  (`params.permit(:category_id, :amount_limit, :period_month, :period_year)`)
  é passado direto para `current_user.budgets.build`/`@budget.update` em
  `create`/`update`, sem checar se `category_id` pertence a
  `current_user.categories`.
- **Evidência da exploração:** `app/services/budget_engine.rb#summary`
  itera `@user.budgets` (corretamente escopado) mas lê `budget.category.name`,
  `budget.category.icon` e `budget.category.natureza` (linhas 25-27) — se o
  `category_id` do budget foi setado para o ID de uma categoria de outro
  usuário, esses três campos vazam atributos da categoria alheia na resposta
  de `#summary`. O `spent` (linha 11-14) continua correto, pois é calculado
  sobre `@user.transactions` — o vazamento é de metadado de categoria, não de
  valores financeiros de terceiros.
- **Probabilidade:** alta — requer só adivinhar/enumerar um `category_id`
  sequencial válido de outro usuário e chamar `POST /budgets` ou
  `PATCH /budgets/:id`.
- **Recomendação:** em `budgets_controller.rb`, revalidar
  `current_user.categories.exists?(id: budget_params[:category_id])` antes de
  salvar (ou usar `current_user.categories.find(...)` para atribuir a
  associação em vez do FK cru).
- **CWE:** CWE-639 (Authorization Bypass Through User-Controlled Key). OWASP
  API1:2023 (Broken Object Level Authorization).

### H2 — BOLA: `Transaction`/`Investment` aceitam `account_id`/`category_id`/`member_id` de outro usuário

- **Onde:**
  - `app/controllers/api/v1/transactions_controller.rb#update` (linhas 33-39)
    chama `@transaction.update(transaction_params)` e `transaction_params`
    (linhas 54-56) permite `:account_id, :category_id, :member_id` sem
    revalidação — diferente de `#create` (linha 21), que ao menos redefine
    `txn.account` via `current_user.accounts.find_by(id: txn.account_id)`
    (mas não faz o mesmo para `category_id`/`member_id`, nem em `create` nem
    em `update`).
  - `app/controllers/api/v1/investments_controller.rb#create` (linha 21) e
    `#update` (linha 30) chamam `current_user.investments.build`/
    `@investment.update` com `investment_params` (linhas 51-52, inclui
    `:account_id`) sem nenhuma revalidação — pior que `transactions#create`,
    pois nem o `account_id` é redefinido a partir de `current_user.accounts`.
- **Impacto:** um usuário autenticado pode criar/editar uma transação ou
  investimento próprio apontando para `account_id`/`category_id`/`member_id`
  de outro usuário — a linha passa a aparecer nos totais/saldo da conta
  alheia (via `Account#transactions`/agregações), e o autor original do
  registro não tem como saber que o dado foi "injetado" de fora.
- **Probabilidade:** alta — mesmo padrão de `category_id` sequencial
  adivinhável do H1.
- **Recomendação:** em ambos os controllers, revalidar cada FK recebido
  contra a associação correspondente de `current_user` antes de
  criar/atualizar (`current_user.accounts.find(params[:account_id])` etc.),
  em vez de aceitar o ID cru via `params.permit`.
- **CWE:** CWE-639. OWASP API1:2023.

### H3 — Mesmo padrão de BOLA no fluxo de importação (CSV/PDF)

- **Onde:** `app/controllers/api/v1/imports_controller.rb` repassa
  `params[:account_id]` direto para `CsvImportService.new(@current_user,
  file, account_id: params[:account_id])` e `PdfImportService.new(@current_user,
  account_id: params[:account_id])`; `#confirm` também repassa `member_id`
  por linha via `confirm_rows` (`params.permit(rows: [..., :member_id])`).
  Ambos os services delegam a persistência para
  `BankImport::TransactionWriter#write!`, que cria a transação via
  `@user.transactions.create!(...)` (então `user_id` está sempre correto),
  mas usa `account_id`/`member_id` recebidos sem checar se pertencem a
  `@user.accounts`/`@user.members`.
- **Impacto:** um CSV/PDF importado por um usuário pode gravar transações
  contra a conta ou o portador (`member_id`) de outro usuário, com o mesmo
  efeito prático do H2 — apenas via um vetor de entrada diferente (upload de
  arquivo em vez de JSON direto).
- **Probabilidade:** alta — o `account_id` é passado como parâmetro de
  formulário/query, sem necessidade de manipular o conteúdo do arquivo.
- **Recomendação:** validar `account_id` contra `@user.accounts` e
  `member_id` contra `@user.members` dentro de
  `BankImport::TransactionWriter#write!` (ponto único, reusado por CSV e
  PDF) — não depender de cada controller/service fazer isso individualmente.
- **CWE:** CWE-639. OWASP API1:2023.

### H4 — `activestorage 8.1.3` — CVE-2026-66066 (GHSA-xr9x-r78c-5hrm)

- **Onde:** `Gemfile.lock` fixa `activestorage (= 8.1.3)`, confirmado
  vulnerável via `bundle exec bundler-audit check --update` (2026-07-29).
- **Descrição:** leitura arbitrária de arquivo e possível execução remota de
  código no processamento de variantes do Active Storage.
- **Mitigação atual:** ActiveStorage não está configurado/em uso ativo no
  Klipper (sem `has_one_attached`/`has_many_attached` em uso, sem rota de
  upload de anexo) — a superfície de ataque (endpoint de variant processing)
  não está exposta hoje.
- **Recomendação:** atualizar para `>= 8.1.3.1` mesmo assim (correção
  gratuita, sem exposição conhecida hoje) ou documentar aceite explícito do
  risco residual.
- **Solução upstream:** `~> 7.2.3.1`, `~> 8.0.5.1`, `>= 8.1.3.1`.

## Médio

### M1 — JWT não é revogado na troca de senha

- **Onde:** `app/controllers/api/v1/users_controller.rb#password` atualiza a
  senha mas não chama `@current_user.increment!(:token_version)` (isso só
  acontece em `#logout`). `app/services/jwt_service.rb` usa `EXPIRY =
  30.days` fixo.
- **Impacto:** um token roubado antes da troca de senha continua válido por
  até 30 dias após a troca — a troca de senha não invalida sessões
  existentes.
- **Recomendação:** incrementar `token_version` também em `#password`, e
  validar `token_version` do payload contra o valor atual do usuário em toda
  requisição autenticada (conferir se isso já ocorre em `BaseController`).

### M2 — Ausência de rate limiting (`rack-attack` não presente)

- **Onde:** `Gemfile`/`Gemfile.lock` não têm `rack-attack` nem equivalente;
  `auth_controller.rb#sign_in`/`#sign_up` não têm nenhum throttle.
- **Impacto:** força bruta de senha e enumeração de e-mail sem limite de
  tentativas.
- **Recomendação:** adicionar `rack-attack` com throttle em
  `/auth/sign_in`/`/auth/sign_up` por IP e por e-mail.

### M3 — `force_ssl` desabilitado em produção

- **Onde:** `config/environments/production.rb:25` —
  `# config.force_ssl = true` comentado.
- **Impacto:** requisições HTTP puro não são forçadas a redirecionar para
  HTTPS a nível de aplicação (mitigado se o proxy/CDN de produção já força
  HTTPS — não verificado nesta auditoria qual é a configuração de
  infraestrutura efetiva do Render/Vercel).
- **Recomendação:** habilitar `config.force_ssl = true` como defesa em
  profundidade, independente da camada de infraestrutura.

### M4 — `loofah`/`rails-html-sanitizer` desatualizados (hardening contínuo)

- **Onde:** `bundle exec bundler-audit check --update` (2026-07-29): `loofah
  2.25.1` com 3 advisories (`GHSA-5qhf-9phg-95m2`, `GHSA-8whx-365g-h9vv`,
  `GHSA-9wjq-cp2p-hrgf` — bypass de detecção de `javascript:` URI e de
  restrição de referência local em SVG); `rails-html-sanitizer 1.7.0`
  (`GHSA-cj75-f6xr-r4g7` — XSS em certas configurações).
- **Natureza do item:** dependência transitiva do Rails — não há uso direto
  de sanitização de HTML de usuário identificado no Klipper hoje, mas a gem
  está no dependency tree. Tratar como **manutenção recorrente**: bump para
  `loofah >= 2.25.2` / `rails-html-sanitizer >= 1.7.1` agora; depois disso,
  cabe ao Dependabot (ver L9) manter atualizado sem virar item de roadmap
  novo a cada release.

### M5 — Dependências npm vulneráveis em `klipper-web`/`quebec-web` (hardening contínuo)

- **Onde:** `npm audit --production` (2026-07-29) em `apps/klipper-web`: 10
  vulnerabilidades (1 crítica, 7 altas, 2 moderadas) — `tar <=7.5.20`
  (crítica, múltiplos DoS/crash — `GHSA-w8wr-v893-vjvp`,
  `GHSA-23hp-3jrh-7fpw`, `GHSA-8x88-c5mf-7j5w`, `GHSA-gvwx-54wh-qm9j`,
  `GHSA-r292-9mhp-454m`), `shell-quote <=1.8.4` (alta, ReDoS —
  `GHSA-395f-4hp3-45gv`), `svgo 3.0.0-3.3.3 || 4.0.0-4.0.1` (alta, script não
  removido por `removeScripts` — `GHSA-2p49-hgcm-8545`), `sharp`/`ipx`/
  `@nuxt/image` (cadeia transitiva). `apps/quebec-web` apresenta perfil
  equivalente (mesma stack Nuxt).
- **Natureza do item:** todas são dependências de build/dev-time (`tar`,
  `postcss`, `esbuild`, `svgo`, `sharp` via `@nuxt/image`) — nenhuma roda em
  runtime de produção server-side exposto a input de usuário não confiável
  diretamente. Tratar como **manutenção recorrente**: `npm audit fix`
  primeiro (não-breaking); avaliar separadamente o bump breaking de
  `@nuxt/image` (`npm audit fix --force`). A partir da correção inicial,
  manter via Dependabot (ver L9, que hoje não cobre ecossistema `npm`).

### M6 — JWT em cookie não-`httpOnly`

- **Onde:** `apps/klipper-web/composables/useApi.ts:3-7` —
  `useCookie<string | null>('klipper_token', { sameSite: 'lax', secure:
  import.meta.env.PROD, maxAge: 60*60*24*30 })`, sem opção `httpOnly` (e o
  Nuxt `useCookie` client-side não tem como setar `httpOnly`, que só pode ser
  definido por resposta de servidor).
- **Impacto:** qualquer XSS bem-sucedido na SPA teria acesso direto ao
  token JWT via `document.cookie`/`js-cookie`, permitindo exfiltração de
  sessão. (Nenhuma XSS foi encontrada nesta auditoria — ver seção
  "Verificado / sem achados" — mas o cookie não é defesa em profundidade
  contra uma futura.)
- **Recomendação:** mover a emissão do cookie para o backend (Rails) como
  `httpOnly` + `secure` + `sameSite=strict`, com o Nuxt lendo apenas um flag
  de "autenticado" não sensível no client, ou aceitar o risco documentadamente
  dado o perfil de uso solo atual.

### M7 — Risco de prompt injection indireta (LLM01) em `agent-pr-review.yml`

- **Onde:** `.github/workflows/agent-pr-review.yml` roda em qualquer
  `pull_request` (`opened`/`synchronize`/`reopened`) — incluindo PRs de forks,
  já que o repositório `Borussia80/Klipper` é **público**. O job busca o
  diff real via `gh pr diff` (conteúdo controlado pelo autor do PR) e
  entrega esse conteúdo a um agente Claude Code com
  `--allowedTools "Read,Grep,Glob,Bash,Write"` e `GH_TOKEN`/
  `CLAUDE_CODE_OAUTH_TOKEN` no mesmo escopo de execução.
- **Natureza do risco:** não é injeção clássica de script do GitHub Actions
  (não há `${{ github.event.pull_request.* }}` interpolado diretamente em um
  bloco `run:` — confirmado ausente) — é risco de **prompt injection
  indireta**: um diff de PR malicioso poderia conter texto formulado para
  tentar induzir o agente LLM a executar ações fora do pretendido, dentro do
  escopo de ferramentas (`Bash`, `Write`) e do `GH_TOKEN` que o job já
  possui.
- **Recomendação:** considerar rodar a revisão de PRs de forks em um
  ambiente com `GH_TOKEN` de escopo mínimo (sem `pull-requests: write` amplo)
  ou exigir aprovação manual (`workflow_dispatch` apenas) para PRs originados
  fora do repositório, revisando a política de "primeira execução requer
  aprovação de mantenedor" que o GitHub já aplica a forks por padrão.
- **Referência:** OWASP LLM Top 10 — LLM01 (Prompt Injection).

## Baixo

> Os 10 achados abaixo são de baixo risco individual e ficam agrupados por
> tema no roadmap (`SEC-14`/`SEC-15`/`SEC-16`) — os IDs `L1`-`L10` abaixo são
> a referência técnica individual de cada um.

### Grupo — Importação (`SEC-14` no roadmap)

- **L1 — `ArgumentError` não tratado no parser de CSV.**
  `app/services/bank_import/amount_parser.rb#call` faz `BigDecimal(s)` após
  limpar a string; se `s` ficar vazia/malformada (ex.: coluna "Valor" sem
  dígitos), `BigDecimal("")` levanta `ArgumentError`.
  `app/services/csv_import_service.rb#import_row` só tem `rescue
  CSV::MalformedCSVError` (no `#call`) e `rescue Date::Error`/
  `ActiveRecord::RecordInvalid` (no `#import_row`) — nenhum `rescue
  ArgumentError`, então uma linha de CSV com valor malformado derruba a
  requisição inteira com 500 em vez de reportar erro por linha.
- **L2 — Exceção não tratada no `#preview` de PDF.**
  `app/services/pdf_import_service.rb#preview` (linhas 21-40) só rescata
  `PDF::Reader::MalformedPDFError` e `PdfAdapters::ParseError` — uma
  exceção de parsing de data (`Date::Error`/`ArgumentError`) dentro de
  `adapter_class.new(pages).parse` (linha 29) ou `serialize_row` (linha 33)
  propaga sem tratamento. Note que `#confirm` (linhas 42-59) já tem um
  `rescue => e` genérico por linha — só o `#preview` está desprotegido.
- **L4 — Sem limite de tamanho de arquivo no import.** Nenhuma validação de
  `content_length`/tamanho encontrada em `imports_controller.rb`,
  `csv_import_service.rb` ou `pdf_import_service.rb`.
- **L5 — Sem validação de magic bytes no import.** O arquivo enviado
  (CSV ou PDF) não tem o conteúdo binário validado contra o tipo esperado
  antes do parsing — só o nome do parâmetro (`file`) e a rota (`/imports` vs
  `/imports/preview`) determinam qual parser roda.

### Grupo — Infraestrutura (`SEC-15` no roadmap)

- **L7 — `config.hosts` irrestrito.** `config/environments/production.rb:61`
  — `# config.hosts = [` comentado, ou seja, o Rails aceita qualquer
  `Host:` header em produção (proteção contra DNS rebinding desabilitada).
- **L8 — GitHub Actions pinadas por tag mutável.** Todos os `uses:` em
  `ci.yml`, `agent-full-report.yml` e `agent-pr-review.yml` usam tags como
  `@v4`/`@v1`/`@v6` (mutáveis, o autor da action pode mover a tag) em vez de
  pin por commit SHA imutável.
- **L9 — Dependabot sem ecossistema `npm`.** `.github/dependabot.yml` só
  configura `bundler` (`/apps/klipper-api`) e `github-actions` (`/`) — sem
  entrada `npm` para `apps/klipper-web`/`apps/quebec-web`, apesar dos 10
  achados do M5 estarem justamente nesse ecossistema.

### Grupo — Aplicação (`SEC-16` no roadmap)

- **L3 — Timing attack em `sign_in`.**
  `app/controllers/api/v1/auth_controller.rb#sign_in` faz `User.find_by(email:
  ...)` e só chama `user&.authenticate(...)` se `user` não for `nil` — quando
  o e-mail não existe, o `bcrypt` nunca roda, tornando a resposta
  mensuravelmente mais rápida do que quando o e-mail existe (senha errada) —
  permite inferir por tempo de resposta se um e-mail está cadastrado.
- **L6 — Troca de e-mail sem reautenticação.**
  `app/controllers/api/v1/users_controller.rb#update` permite `:email` via
  `update_params` sem exigir `current_password`, diferente da ação
  dedicada `#password` (que exige). Uma sessão sequestrada (ex.: aba
  destravada) pode trocar o e-mail de recuperação sem confirmar a senha
  atual.
- **L10 — Service Worker cacheia respostas financeiras em disco.**
  `apps/klipper-web/nuxt.config.ts` (bloco `pwa.workbox.runtimeCaching`,
  linhas 68-77) usa `NetworkFirst` para `/api/v1/.*` com `cacheName:
  'klipper-rails-api'` e `maxAgeSeconds: 60` — respostas de saldo/transação
  ficam até 60s no Cache Storage do navegador, em disco, em vez de só em
  memória; risco baixo (janela curta) mas real em dispositivo compartilhado.

## Verificado / sem achados

Itens explicitamente checados nesta auditoria e **sem evidência de
vulnerabilidade**:

- **SQL injection:** nenhum uso de SQL raw interpolando input de usuário
  encontrado (Brakeman: 0 warnings de SQL Injection).
- **Mass assignment via `permit!`:** nenhuma ocorrência de `params.permit!`
  no código.
- **IDOR clássico por `:id` na URL:** os 6 controllers principais
  (`accounts`, `categories`, `members`, `transactions`, `investments`,
  `budgets`) escopam corretamente via `current_user.<associação>.find(params[:id])`
  no `show`/`update`/`destroy` — o problema encontrado (H1/H2/H3) é
  especificamente em **FKs internos ao payload**, não no `:id` do recurso
  principal.
- **JWT algorithm confusion:** `JwtService.decode` fixa `algorithm: "HS256"`
  explicitamente na chamada de `JWT.decode` — não aceita `alg: none` nem
  troca para RS256.
- **Armazenamento de senha:** `has_secure_password` (bcrypt), sem achado.
- **Precisão monetária:** uso consistente de `Decimal`/`BigDecimal` nos
  cálculos financeiros verificados (`budget_engine.rb`, `amount_parser.rb`).
- **Log de dados sensíveis:** nenhuma ocorrência de log direto de senha/token
  encontrada; filtros de parâmetro padrão do Rails presentes.
- **CORS:** origem específica configurada, sem wildcard `*` com credenciais.
- **XSS via `v-html`:** nenhuma ocorrência de `v-html` renderizando dado
  vindo de input de usuário.
- **CSRF:** não aplicável — API stateless com JWT em `Authorization` header
  (fora do cookie, que é só transporte — ver M6 sobre o cookie em si).
- **`pull_request_target` em workflows:** não usado em nenhum workflow do
  repositório.
- **Segredos ecoados em log de CI:** nenhuma ocorrência encontrada nos
  workflows atuais.
- **Dockerfile:** build multi-stage, usuário não-root confirmado.
- **ActiveStorage — download arbitrário:** não aplicável, ActiveStorage não
  está configurado/em uso (ver H4).
