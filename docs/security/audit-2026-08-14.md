## Médio

### M8 — `imports/confirm` não revalida `amount`/`description`/`occurred_on` contra o documento original

- **Onde:** `app/controllers/api/v1/imports_controller.rb#confirm` (método
  `confirm_rows`, linha 48-51) repassa `rows` direto de `params` para
  `PdfImportService#confirm`; `app/services/pdf_import_service.rb` (comentário
  do próprio arquivo documenta o design: *"O `#confirm` recebe de volta
  exatamente o array de rows que o `#preview` devolveu"*) monta cada
  transação a partir de `BigDecimal(row[:amount])`/`Date.parse(row[:occurred_on])`
  vindos do payload, sem nenhum vínculo (id de preview, hash, assinatura) ao
  PDF originalmente processado em `#preview`.
- **Impacto:** o fluxo de `account_id`/`member_id` **é** validado contra posse
  do usuário (`BankImport::TransactionWriter#write!`, corrigido por `SEC-05`),
  mas os campos financeiros da própria linha — `amount`, `description`,
  `occurred_on`, `installment_number`/`installment_total` — não são
  re-derivados nem cross-checados contra o arquivo fonte. Um usuário
  autenticado que capture a resposta de `POST /imports/preview` pode reenviar
  `POST /imports/confirm` com esses valores adulterados, e a transação é
  persistida como se fosse fiel ao extrato/fatura original. O blast radius é
  limitado aos próprios dados do usuário autenticado (não há exposição
  cross-user aqui — isso já foi coberto por `H3`/`SEC-05`), mas compromete a
  confiabilidade do dado financeiro importado como espelho fiel do documento
  bancário, inclusive para relatórios (`net_worth`, `debt_ranking`) que
  consomem essas transações depois.
- **Probabilidade:** alta para um usuário mal-intencionado consigo mesmo
  (ex.: inflar categoria de gasto dedutível, mascarar valor real de uma
  compra); não aplicável a ataque cross-user sem encadear com outro achado.
- **Recomendação:** vincular `confirm` a uma referência server-side do
  `preview` (ex.: cachear `result.rows` em `Rails.cache`/tabela temporária sob
  um `preview_id` de vida curta, e `confirm` receber apenas
  `preview_id` + lista de índices/flags de linhas confirmadas — nunca os
  valores financeiros propriamente ditos). Alternativa mais simples: gerar um
  HMAC assinado por linha no `preview` (com `amount`/`occurred_on`/`description`
  como payload do hash) e exigir que `confirm` reenvie esse hash por linha,
  rejeitando qualquer linha cujo hash não bata com os valores recebidos.
- **CWE:** CWE-345 (Insufficient Verification of Data Authenticity). OWASP
  Top 10 2021 — A08 (Software and Data Integrity Failures).

## Baixo

### L11 — `/api/v1/kira/chat` referenciado no frontend, ausente no backend

- **Onde:** `apps/klipper-web/pages/kira.vue:161` chama
  `apiFetch('/api/v1/kira/chat', ...)`. Busca em
  `apps/klipper-api/config/routes.rb` e em todo `apps/klipper-api/app/controllers`
  não encontra nenhuma rota/controller correspondente — a única ocorrência de
  "kira" no backend é uma linha em `log/test.log` (indício de que a requisição
  já foi tentada e retornou 404 em algum momento).
- **Impacto:** hoje, nenhum — é uma chamada que falha (404), não uma
  superfície de ataque ativa. Registrado como achado de robustez/rastreio,
  não de exploração.
- **Recomendação:** quando este endpoint for implementado, revisar
  especificamente: autenticação (`before_action :authenticate_request!`),
  isolamento de dados entre usuários/households (o assistente aparentemente
  teria acesso a patrimônio/orçamento do usuário autenticado — garantir que o
  contexto passado ao LLM é sempre escopado por `current_user`), e resistência
  a prompt injection via mensagens do usuário. Até lá, nenhuma ação é
  necessária além de confirmar com o time se é feature em desenvolvimento ou
  código morto a remover.
- **CWE:** não aplicável (não é uma vulnerabilidade ativa).
