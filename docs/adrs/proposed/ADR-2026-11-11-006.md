# Atualizar nuxt de 3.21.11 para 4.6.4+ em klipper-web e quebec-web

## Contexto

O Finding `SEC-007` (`nuxt-core-pinned-3-21-accumulated-moderate-cves`)
identificou que os dois frontends do monorepo — `apps/klipper-web` e
`apps/quebec-web` — seguem pinados em `nuxt@3.21.11`
(`apps/klipper-web/package.json:22`, `apps/quebec-web/package.json:13`, ambos
com `"nuxt": "^3.15.4"`). Desde a última auditoria, quatro advisories
moderate/low novas passaram a atingir essa linha 3.x, incluindo um vetor de
XSS em server islands e um bypass de route rules por path case-variant.

Por serem moderate/low, esses avisos atravessam `.github/scripts/audit-gate.mjs`
sem alarme: o portão (`BLOQUEIA = new Set(['high', 'critical'])`, linha 15)
só falha o CI para `high`/`critical`, deixando a linha 3.x acumular dívida de
segurança moderate/low de forma silenciosa a cada novo PR.

A auditoria já reduziu a incerteza sobre explorabilidade real hoje: grep por
`NuxtIsland`/server island em `apps/klipper-web` e `apps/quebec-web` não
retornou nenhuma ocorrência, e os `to=` de `<NuxtLink>` encontrados no código
de `klipper-web` são strings estáticas ou IDs de registros do próprio
usuário, não input livre de terceiros. Isso reduz a explorabilidade das duas
CVEs de XSS/route-rule no estado atual do código, mas não a elimina enquanto
a versão vulnerável permanecer em produção — qualquer novo uso de server
island ou de `to=` dinâmico a partir de input externo reabriria a exposição
sem que o CI reagisse.

## Decisão proposta

Planejar e executar o bump de `nuxt` de `^3.15.4` (resolvido em 3.21.11) para
`^4.6.4` nos dois apps (`klipper-web` e `quebec-web`), tratando-o como major
com risco de breaking changes a testar explicitamente — não como patch
automático via Dependabot/Renovate.

Alternativas consideradas:

1. **Manter 3.x e aceitar a exceção em `audit-gate.mjs`** — rejeitada: o
   próprio comentário do gate (linha 8, referência a `SEC-003`) documenta que
   um portão silenciosamente tolerante é um portão que se aprende a ignorar;
   formalizar uma exceção permanente para CVEs acumuladas repetiria esse
   padrão.
2. **Rebaixar o limiar do gate para bloquear também moderate/low** —
   rejeitada como solução isolada: travaria o CI em avisos moderate/low sem
   correção disponível em outras dependências transitivas, reproduzindo o
   problema original que motivou a lista de exceções (comentário de
   `audit-gate.mjs`).
3. **Bump para 4.6.4+ (recomendada)** — resolve a causa raiz (versão
   vulnerável) em vez de mascarar o sintoma no gate, e é consistente com o
   `CLAUDE.md` do repositório, que já declara a stack-alvo como "Nuxt 4 +
   Rails 8" (`_shared-contract.md`, seção "Domínio do projeto").

## Consequências

Resolve as quatro CVEs moderate/low na raiz, eliminando a dependência de uma
mitigação informal (ausência de server islands e de `to=` dinâmico) que pode
deixar de valer silenciosamente em PRs futuros.

Exige esforço de migração e teste em dois apps simultaneamente (major bump
de framework): suíte de testes (Vitest em `klipper-web`), build de produção
na Vercel e verificação manual das rotas/PWA precisam ser revalidados antes
do merge. Evidence unavailable quanto ao escopo exato de breaking changes
entre Nuxt 3.21 e 4.6 para as dependências específicas deste repositório
(`@vite-pwa/nuxt`, `@nuxt/image`, `@nuxt/fonts`, `@nuxt/eslint`) — isso só é
observável executando a migração.

Enquanto o bump não é concluído, a exposição residual documentada no
Finding (ausência de server islands, `to=` não dinâmico) continua sendo a
única mitigação real; qualquer PR que introduza um desses padrões antes da
migração reabre a exposição sem que o CI atual sinalize.
