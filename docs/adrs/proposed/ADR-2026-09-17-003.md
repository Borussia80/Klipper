# Formalizar a exposição residual do access token em cookie legível por JS

## Contexto

O Finding `SEC-006` aponta uma assimetria na estratégia de armazenamento de
tokens do SPA Nuxt: o access token JWT (validade de 15 minutos) é guardado
em `klipper_token`, um cookie **sem** `httpOnly`, definido em
`apps/klipper-web/composables/useApi.ts:18-22` via `useCookie`, e lido em
JavaScript no `onRequest` do `$fetch` (linhas 31-38) para montar o header
`Authorization: Bearer`. Já o refresh token é gravado pelo backend em
`apps/klipper-api/app/controllers/api/v1/auth_controller.rb:59-61` como
`cookies[:klipper_refresh]` com `httponly: true` — inacessível a
JavaScript.

Essa assimetria é deliberada: o front depende de ler o access token para
montar o header `Authorization` a cada chamada (`useApi.ts:32-37`), o que
exige que o cookie seja legível em JS. O refresh token, por sua vez, nunca
precisa ser lido pelo front — só é enviado automaticamente pelo browser ao
endpoint de refresh — e por isso pôde ser marcado `httpOnly`.

Não foi encontrado, nesta auditoria, nenhum sink de XSS explorável no
código do SPA que leia esse cookie. O finding é sobre defesa em profundidade
insuficiente caso um XSS venha a existir no futuro, não sobre uma
vulnerabilidade confirmada hoje.

## Decisão proposta

Formalizar a exposição residual como aceita, documentando-a como uma
decisão consciente em vez de uma lacuna não registrada, e mitigar o risco
residual com uma Content-Security-Policy no Nuxt restringindo `script-src`
para reduzir a chance de um XSS futuro conseguir executar e ler o cookie.

Alternativas consideradas:

- Mover o access token para um cookie `httpOnly` lido só pelo backend,
  substituindo o fluxo de `Authorization: Bearer` por autenticação baseada
  em cookie com CSRF token. Tecnicamente mais forte contra roubo de token
  via XSS, mas exige reescrever o fluxo de autenticação inteiro do
  `useApi.ts` (montagem do header, renovação em `withRenewal`,
  `apiFetch.raw` usado por `useTransactions`) e adicionar geração/validação
  de CSRF token no backend Rails — escopo bem maior que o risco residual
  observado justifica hoje, dado que nenhum sink de XSS explorável foi
  encontrado.
- Não fazer nada. Rejeitada: deixaria a assimetria sem registro, obrigando
  cada auditoria futura a redescobrir e reavaliar a mesma questão do zero.

Recomenda-se a formalização com CSP como decisão proposta neste ADR, por
reduzir a superfície de ataque real (impedir que um XSS injete script
executável) sem o custo de reescrever o fluxo de autenticação.

## Consequências

Documentar a exposição como aceita evita que a mesma questão seja
redescoberta como finding novo em auditorias futuras sem contexto de que já
foi avaliada e a decisão foi consciente. Adicionar CSP reduz a probabilidade
de um XSS conseguir rodar script capaz de ler `klipper_token`, mas não
elimina o vetor — se um XSS conseguir contornar a CSP (ex: via
`unsafe-inline` necessário por alguma dependência), o access token continua
lido em texto claro por 15 minutos de validade.

Evidence unavailable quanto ao conjunto de diretivas CSP necessárias — não
há levantamento no checkout de quais scripts/estilos inline o Nuxt ou suas
dependências exigem hoje; definir a política exata requer auditar o build
de produção, fora do escopo desta auditoria.
