# Mover permissions de GITHUB_TOKEN do workflow-level para job-level em agent-full-report.yml

## Contexto

O Finding `SEC-007` identifica que `.github/workflows/agent-full-report.yml`
declara `permissions: contents: write`, `pull-requests: write` e
`id-token: write` no nível do workflow (linhas 22-27), o que faz todo job
do workflow herdar essas credenciais de escrita — incluindo o job
`run-agents` (linhas 94-144).

`run-agents` roda em matriz um agente Claude por item de
`needs.guard.outputs.agents_json` (`["architecture","security","finance"]`
no modo fast ou mais `"runtime"`/`"ux"` no modo deep, resolvido em
linhas 88-92), cada um com `claude_args: --allowedTools
"Read,Grep,Glob,Bash,Write"` (linha 122) e Bash irrestrito, lendo o
checkout inteiro do repositório (o comentário nas linhas 117-120 confirma
que o agente de segurança já varreu "os três apps" até quase esgotar o
teto de turnos). Nenhum desses agentes chama `peter-evans/create-pull-request`
ou qualquer API de escrita do GitHub — eles apenas escrevem um JSON local em
`$OUTPUT_PATH` (linha 134) que depois é subido como artifact (linhas
139-144). Só o job `aggregate` (linhas 146-269) de fato usa escrita: é
quem chama `peter-evans/create-pull-request@...` na linha 247 para abrir o
PR automático do relatório.

Ou seja, os cinco agentes de auditoria rodam com `contents: write` +
`pull-requests: write` no ambiente sem nunca precisar dessas credenciais
para o que produzem — exatamente o cenário de LLM01/prompt injection em que
conteúdo não confiável lido durante a varredura do repositório poderia
induzir o agente a usar um `GITHUB_TOKEN` de escrita que ele não deveria
ter em primeiro lugar.

O workflow `.github/workflows/agent-pr-review.yml` já trata um risco
correlato: declara `permissions: contents: read` (não `write`) no nível do
workflow e, via comentário nas suas próprias linhas de guard-rail, explica
que PR de fork só roda via `workflow_dispatch` manual porque "PR de fork tem
Bash + GH_TOKEN disponíveis ao agente" (SEC-13/LLM01). `agent-full-report.yml`
não tem um guard-rail equivalente para o `run-agents` — o único
`contents: write` do workflow aplica-se indistintamente a todos os jobs,
incluindo os que leem conteúdo não confiável do repositório inteiro sem
precisar escrever nada.

## Decisão proposta

Mover o bloco `permissions:` de workflow-level para job-level em
`agent-full-report.yml`, como já recomendado no finding:

- Job `run-agents`: `contents: read` (ou bloco de permissions vazio/omitido
  — cada perna da matriz só faz checkout e escreve seu próprio partial
  local em `runner.temp`, nunca interage com a API do GitHub).
- Job `aggregate`: mantém `contents: write` e `pull-requests: write`, já
  que é o único que chama `peter-evans/create-pull-request`.
- Job `guard`: hoje só faz checkout e lê `git log` para o anti-loop
  (linhas 56-73) — não escreve nada, então também pode ficar com
  `contents: read`.
- `id-token: write` permanece necessário onde a `claude-code-action` troca
  o token OIDC (comentário nas linhas 25-27 já documenta essa dependência)
  — ou seja, em todos os jobs que invocam a action, incluindo `run-agents`;
  só os escopos de escrita no conteúdo/PRs do repositório é que precisam
  ficar restritos ao `aggregate`.

Essa mudança não altera o que os agentes de auditoria produzem hoje — eles
já só escrevem em `$OUTPUT_PATH` local — apenas remove do ambiente deles uma
credencial que nunca usam.

## Consequências

- **Melhora:** reduz o raio de uma eventual injeção de prompt durante a
  varredura do repositório inteiro (os cinco agentes de `run-agents`) de
  "capacidade de escrever conteúdo/abrir PR no GitHub" para zero capacidade
  de escrita — a mesma redução de superfície que `agent-pr-review.yml` já
  aplica para o seu próprio fluxo.
- **O que fica mais caro/arriscado:** nenhum custo identificado — o
  `run-agents` não usa escrita hoje, então restringi-la não remove
  funcionalidade observável no pipeline atual.
- **O que precisa ser migrado:** apenas a estrutura do YAML (mover o bloco
  `permissions:` para dentro de cada `jobs.<nome>:`); não há mudança de
  código em `.github/scripts/*.mjs` nem nos prompts dos agentes.
- **Impacto em runs futuros caso um agente precise escrever algo no
  GitHub:** Evidence unavailable — não há indicação no workflow atual de
  que algum dos cinco agentes de auditoria venha a precisar dessa
  capacidade; se isso mudar, a permissão teria que ser adicionada de volta
  explicitamente para o job correspondente.
