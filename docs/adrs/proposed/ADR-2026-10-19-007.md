# Extrair componente/classes utilitárias para o padrão visual de campo select

## Contexto

O Finding `ARCH-014` aponta que o padrão visual de campo com `<select>`
(label, wrapper posicionado, seta customizada via `appearance: none` +
caractere `▾` posicionado em absoluto) está reimplementado em CSS scoped
duplicado em pelo menos cinco modais de entidade diferentes.

Evidência observada no checkout — duas variantes do mesmo padrão,
copiadas com nomes de classe e valores já divergentes entre si:

- Variante A (`.select-wrap` / `.select` / `.select-arrow`), idêntica byte
  a byte entre `ModalNovoLancamento.vue:266-287` e
  `ModalEditarLancamento.vue:271-292`: `padding-right: 28px`, seta em
  `right: 10px; transform: translateY(-50%)`.
- Variante B (`.sel-wrap` / `.fi-sel` / `.sel-caret`), idêntica byte a byte
  entre `ModalNovoMembro.vue:87-108`, `ModalNovaConta.vue:123-145` e
  `ModalEditarReembolso.vue:78-99`: `padding-right: 32px`, seta em
  `right: 11px; transform: translateY(-60%)`.
- As duas variantes já divergiram no espaçamento (`28px` vs `32px`) e na
  posição vertical da seta (`-50%` vs `-60%`), confirmando exatamente o
  risco descrito no finding: ajustes visuais feitos em uma cópia não se
  propagam para as outras.
- Em `ModalNovaCategoria.vue:50-54` o `<select>` usa as classes
  `class="fi fi-sel"` e `<span class="sel-caret">`, mas o
  `<style scoped>` desse arquivo (`ModalNovaCategoria.vue:202-250`) não
  define `.fi-sel` nem `.sel-caret` — só define `.fi`, `.fi-val` e outras
  classes. Como estilos `scoped` do Vue são isolados por componente (via
  atributo `data-v-*`), esse `<select>` consome nomes de classe do padrão
  compartilhado sem a CSS correspondente estar presente no próprio arquivo,
  ficando sem o tratamento visual (seta customizada / `appearance: none`)
  que as demais variantes aplicam.

## Decisão proposta

Extrair o padrão de campo select (wrapper posicionado + reset de
`appearance` + seta customizada) para um ponto único de definição,
reutilizado por todos os modais de criação/edição de entidade.

Alternativas consideradas:

1. **Componente `BaseSelectField.vue`** (recomendada): encapsula o
   `<div class="select-wrap">` + `<select>` + `<span class="select-arrow">`
   como um componente com `v-model`, `options` (ou slot para `<option>`) e
   `aria-label` via prop. Resolve a duplicação de template e de CSS ao
   mesmo tempo, e torna a classe/estilo inexistente em
   `ModalNovaCategoria.vue` um erro de uso impossível (o componente sempre
   carrega seu próprio estilo).
2. **Classes utilitárias globais em `assets/css`**: move apenas o CSS
   (`.select-wrap`, `.select`, `.select-arrow` com um único nome
   canônico) para uma folha de estilo global não `scoped`. Resolve a
   duplicação de CSS e o caso de `ModalNovaCategoria.vue` sem exigir
   mudança de template, mas não resolve a duplicação do markup
   (`<div class="select-wrap">...<span class="select-arrow">▾</span></div>`)
   repetido em cada modal.

A alternativa 1 é recomendada por eliminar tanto a duplicação de CSS quanto
a de markup, e por remover a possibilidade de um `<select>` referenciar
classes de um padrão compartilhado sem a CSS associada — o problema
concreto já observado em `ModalNovaCategoria.vue`.

## Consequências

- Unifica os dois valores hoje divergentes (`padding-right: 28px` vs
  `32px`; seta em `translateY(-50%)` vs `-60%`) em uma única definição,
  eliminando a inconsistência visual já existente entre modais.
- Corrige o caso de `ModalNovaCategoria.vue`, que hoje referencia classes
  sem estilo correspondente no próprio componente.
- Exige migrar `ModalNovoLancamento.vue`, `ModalEditarLancamento.vue`,
  `ModalNovoMembro.vue`, `ModalNovaConta.vue`, `ModalEditarReembolso.vue` e
  `ModalNovaCategoria.vue` para o novo componente/classes, removendo o CSS
  scoped duplicado de cada um.
- Impacto visual fino (ex: se a posição de seta "correta" deve ser a da
  variante A ou da B) é uma decisão de produto/design, não uma conclusão
  que decorre só do código: Evidence unavailable.
