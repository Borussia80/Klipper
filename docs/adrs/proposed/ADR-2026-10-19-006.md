# Extrair template e CSS comuns dos modais de lançamento para um componente único

## Contexto

O Finding `ARCH-008` aponta que `ModalNovoLancamento.vue` e
`ModalEditarLancamento.vue` já compartilham a lógica de formulário via
`useLancamentoForm()` (ambos desestruturam `accounts, categories, members,
isLoadingData, tipoOpcoes, tipo, valor, descricao, categoria, conta,
portador, data, error, validate, isValid, buildPayload` — `ModalNovoLancamento.vue:128-132`,
`ModalEditarLancamento.vue:135-139`), mas o template de apresentação e o
`<style scoped>` inteiro permanecem duplicados quase byte a byte entre os
dois arquivos.

Evidência observada no checkout:

- O bloco de toggle de tipo, input de valor, descrição, selects de
  categoria/conta/portador e input de data é idêntico elemento a elemento
  entre `ModalNovoLancamento.vue:4-98` e `ModalEditarLancamento.vue:9-103`
  — mesmas classes (`tipo-toggle`, `tipo-btn`, `valor-wrap`, `valor-input`,
  `flbl`, `field`, `select-wrap`, `select`, `select-arrow`, `row-two`),
  mesmos `aria-label`, mesma estrutura de `v-if="isLoadingData"`.
- O `<style scoped>` é idêntico byte a byte entre `ModalNovoLancamento.vue:163-309`
  e `ModalEditarLancamento.vue:168-314` (`.tipo-toggle`, `.tipo-btn`,
  `.valor-wrap`, `.valor-input`, `.flbl`, `.field`, `.select-wrap`,
  `.select`, `.select-arrow`, `.row-two`, `input[type="date"]`, `.cta`).
- As únicas diferenças reais entre os dois arquivos são: o título/subtítulo
  do `UiBaseModal` (`ModalNovoLancamento.vue:2` vs
  `ModalEditarLancamento.vue:2-7`), o rótulo do CTA (`ctaLabel` computed em
  `ModalNovoLancamento.vue:136-140` vs `'Salvar'` fixo em
  `ModalEditarLancamento.vue:121`), a condição de `:disabled` do CTA
  (`ModalEditarLancamento.vue:117` soma `|| !transaction`) e a chamada final
  de submit (`createTransaction` + reset de campos em
  `ModalNovoLancamento.vue:142-160` vs `updateTransaction` + `watch`/`fillFrom`
  em `ModalEditarLancamento.vue:143-165`).

Como o problema está isolado no template/CSS e não na lógica de formulário
(já extraída), qualquer ajuste visual futuro (ex: mudar o estilo do input
de valor ou do select) precisa ser replicado manualmente nos dois arquivos,
com risco real de divergência — o que já é o padrão observado no finding
relacionado `ARCH-014` para o CSS de select reaproveitado em outros modais.

## Decisão proposta

Extrair o template compartilhado (toggle de tipo, valor, descrição,
detalhes de categoria/conta/portador, data, mensagem de erro e CSS scoped
associado) para um componente de apresentação único, ex:
`LancamentoFormFields.vue`, que recebe os `ref`s/estado retornados por
`useLancamentoForm()` via `defineModel`/props e emite um evento de submit
(ou expõe os valores via `v-model` individuais).

Alternativas consideradas:

1. **Componente de apresentação único parametrizado por modo** (recomendada):
   `LancamentoFormFields.vue` recebe `ctaLabel`, `ctaDisabled` e emite
   `@submit`; `ModalNovoLancamento.vue` e `ModalEditarLancamento.vue` ficam
   responsáveis só por título/subtítulo do `UiBaseModal`, pelo cálculo de
   `ctaLabel`/`disabled` específico de cada modo, e pela chamada
   `createTransaction` vs `updateTransaction` + `fillFrom`.
2. **Slot-based composition**: manter um único componente modal com slots
   para as partes que diferem. Mais flexível, porém adiciona indireção para
   um caso onde a diferença real é pequena (3 pontos: título, label do CTA,
   chamada de submit) — não justifica a complexidade extra de slots.

A alternativa 1 é recomendada por manter a divisão de responsabilidade já
estabelecida por `useLancamentoForm()` (lógica no composable, apresentação
no componente de campos, orquestração de modo no modal específico).

## Consequências

- Elimina a duplicação do template e do `<style scoped>` (hoje ~250 linhas
  repetidas entre os dois arquivos), reduzindo o custo de qualquer ajuste
  visual futuro a um único ponto de edição.
- `ModalNovoLancamento.vue` e `ModalEditarLancamento.vue` passam a depender
  de um componente filho adicional, o que exige definir um contrato de
  props/emits explícito (hoje o estado é lido/escrito diretamente nos
  `ref`s do composable dentro do próprio template do modal).
- Os testes existentes (`ModalNovoLancamento.test.ts`,
  `ModalEditarLancamento.test.ts`) precisam ser revisados: qualquer
  asserção que hoje depende de selecionar elementos do formulário
  diretamente na árvore do modal passa a atravessar o componente filho.
- Impacto em performance de runtime: Evidence unavailable.
